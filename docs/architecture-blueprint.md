# Architecture Blueprint — масштабируемая платформа уведомлений

Высокоуровневое описание целевой архитектуры: компоненты, потоки данных и принципы.

---

## Обзор потока

Уведомления проходят путь: **внешние сервисы → приём (ingest) → Kafka → аудит и воркеры → доставка провайдерам → история и read model**.

### Верхнеуровневая схема

```
  [service 1]  [service 2]  ...  [service N]
        \          |                  /
         \         |                 /
          \        v                /
           +----> +------------------+
                  | notification-    |
                  | ingest           |----> Cache (дедупликация)
                  | POST /notifications
                  +--------+---------+
                           |
                           v
                  +------------------+
                  | Kafka            |
                  | notify.p0, p1... |
                  +--------+---------+
                           |
           +---------------+---------------+
           |               |               |
           v               v               v
  +-------------+  +----------------+  +------------------+
  | audit-worker|  | notification-  |  | observability    |
  |             |  | worker         |  | (Prometheus/     |
  | --> PG      |  | (dispatcher)   |  |  Grafana)        |
  | --> metrics |  | templates,     |  +------------------+
  +-------------+  | webhooks       |
                   +-------+--------+
                           |
           +---------------+---------------+
           |                               |
           v                               v
  +----------------+            +------------------+
  | email / push   |            | Kafka (вторая    |
  | / sms providers|            | очередь)         |
  +----------------+            +--------+---------+
                                             |
                                             v
                                    +------------------+
                                    | notification-    |
                                    | history          |
                                    | GET /notifications
                                    | read model --> PG
                                    +------------------+
```

## 1. Слой приёма уведомлений (Notification Ingestion)

### Инициаторы

Слева в схеме — **upstream-сервисы** (other service 1, 2, … N), которые инициируют отправку уведомлений.

### Сервис `notification-ingest`

**Точка входа:** `POST /notifications`

**Цель:** быстро принять запрос и не потерять уведомление («быстро отправить и не потерять»).

**Функции:**

- **Ограничение трафика (429)** — защита от перегрузки, при необходимости ответ HTTP 429 Too Many Requests.
- **Дедупликация** — по **idempotency key**, чтобы один и тот же запрос не обрабатывался дважды.
- **Роутинг** — выбор топика/очереди по **правилам маршрутизации** (например, по типу или приоритету).

**Кэш:** используется для дедупликации по idempotency key. Вариант: локальный кэш + глобальный, но быстрый (например, Redis).

**Реализация:**

1. **Правила маршрутизации** — для небольшого числа типов (например, 4) достаточно конфигурации. При появлении динамики можно вынести в БД.
2. **Кэш** — локальный + глобальный быстрый кэш.

После обработки запроса событие публикуется в **Kafka** в топики вида `notify.p0`, `notify.p1`, `notify.p...` (партиционированные топики для масштабирования).

## 2. Аудит и наблюдаемость (Auditing & Observability)

### `audit-worker`

Потребляет сообщения из первой очереди Kafka (по схеме — пунктирная линия).

- Отправляет данные аудита в платформу **observability (Prometheus/Grafana)**.
- Сохраняет аудит в **PostgreSQL**.

### Observability (Prometheus / Grafana)

Центральный компонент для метрик и дашбордов, получает данные от `audit-worker` и при необходимости от других сервисов.

---

## 3. Обработка и доставка (Notification Processing & Dispatch)

### `notification-worker` (по сути — notify-dispatcher)

Потребляет сообщения об уведомлениях из первой очереди Kafka.

**API:**

- `POST /templates` — создание шаблонов.
- `GET /templates` — получение шаблонов.
- Опционально: `GET /notification-logs`.
- `/webhooks` — приём вебхуков.

**БД (PostgreSQL):** быстрый write-ahead по шаблонам для отправки + кэш с TTL при обновлении (write update).

**Внешние провайдеры:** воркер отправляет уведомления в:

- email provider;
- push provider (Android);
- push provider (iOS);
- sms provider.

После отправки воркер синхронно публикует обновление во **второй экземпляр/топики Kafka** (пост-диспатч поток для истории и согласованности).

---

## 4. История уведомлений и read model

### Сервис `notification-history`

Потребляет сообщения из второй очереди Kafka.

**API:**

- `GET /notifications` — список уведомлений.
- `GET /notifications/unread` — непрочитанные.
- Опционально: `SSE /notifications/stream` — стрим в реальном времени (Server-Sent Events).

**Read model:** хранит статусы, приоритеты, даты и прочую информацию для чтения. Данные хранятся в отдельной **PostgreSQL**.

## Сводка по компонентам

| Компонент              | Роль                                      |
|------------------------|-------------------------------------------|
| notification-ingest    | Приём, лимиты, дедупликация, роутинг, Kafka |
| Kafka (топики notify.*)| Очередь событий, масштабирование          |
| audit-worker           | Аудит, метрики, запись в БД               |
| observability          | Prometheus/Grafana — метрики и дашборды   |
| notification-worker   | Шаблоны, диспатч в провайдеры, вторая Kafka |
| notification-history   | Read model, API истории и непрочитанных   |
| PostgreSQL             | Аудит, шаблоны, read model                |

---

## Принципы

- **Событийная модель** — Kafka как шина событий между ingest, worker и history.
- **Разделение ответственности** — приём, доставка и история вынесены в отдельные сервисы.
- **Устойчивость** — дедупликация, лимиты, персистентность в Kafka и БД.
- **Наблюдаемость** — аудит и метрики с самого начала потока.
